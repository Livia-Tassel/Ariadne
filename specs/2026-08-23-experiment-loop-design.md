# Ariadne v0.1 领域内核设计：实验记录与复盘闭环

日期：2026-08-23（第二版，已评审修订）
状态：已实现并冻结为兼容性基线

> 本文保留事件模型、判定与复盘规则。CLI 交互和“Web GUI 属于范围外”的判断已经过时；当前产品设计以 [`2026-08-25-gui-v0.2-design.md`](2026-08-25-gui-v0.2-design.md) 为准。

## 1. 背景与定位

目标是一个陪伴科研人员从立项到论文的完整工具。完整愿景包含五段：检索下载 → 总结分类 → 精读 → 课题发散 → 实验与论文。

v1 只做**最后一段**：实验的预测、记录、差异分析与复盘。

选择这一段作为起点的理由：

- 现有工具（Elicit、Undermind、SciSpace、Consensus）几乎都集中在前半段的检索与综述，实验环节的「假设—预测—验证—反思」闭环是空白。
- 这一段不依赖论文抓取和 PDF 解析——那是整个项目里最脏、天花板最低（受订阅与法务限制）的两块工程。
- 它每天都能被用上，反馈周期最短。

核心机制来自一个具体的工作方法：**实验开跑之前，先列出表格并写下自己对结果的预测。** 实验结果与预期不符，说明某个假设有问题，此时的反思才是知识增长的来源。

两条贯穿全局的原则：

- **负结果与正结果同等重要。** 最没有价值的是没有任何起伏的实验批次。
- **写论文所需的一切材料，在过程中自然沉淀，而不是最后回头补。**

### 1.1 v1 的验证目标

这个工具唯一的生死风险是**用户愿不愿意在实验开跑前把预测填完**。抽取管线、Excel 导出、自由对话都是效率优化，与这个风险无关。

因此 v1 的范围被压到最小闭环，把交互摩擦最早暴露出来：

```
plan（填预测并锁定） → result（录入实测） → 自动判定 → review（复盘 SURPRISE） → board
```

如果两周自用后发现懒得填预测，那么任何抽取管线都是白写的；反过来，如果预测这一环立住了，抽取只是省时间，晚做没有损失。

## 2. 形态与存储

本地 CLI，纯文件存储，无数据库、无服务端。

```
<project>/
  runs.jsonl           append-only 事件流 —— 唯一真相来源
  board.md             从 runs.jsonl 派生的看板（只读，可重新生成）
  beliefs.md           从 runs.jsonl 派生的信念清单（只读，可重新生成）
  logs/                原始日志与结果文件归档，供追溯
  config.toml          平台 Base URL / 模型角色配置（不含密钥）
```

整个目录可以进 git。

**唯一真相来源是严格的。** 上一版把 `hypothesis.md` 和 `beliefs.md` 作为手写的一手数据，与「`runs.jsonl` 是唯一真相来源」直接冲突：手写文件会被覆写，而事件流里对它们的引用会在事后无法还原。本版取消这两个手写文件——假设与信念都以事件形式进入 `runs.jsonl`，`beliefs.md` 与 `board.md` 一样是派生产物，可随时用 `ari board` 重新生成，删掉不丢数据。

选择文件而非 SQLite 的理由：可 diff、可版本控制、可被人直接读、崩溃后可手工修复。代价是复杂查询较弱，但 v1 的数据量（单项目数百行）不构成问题。

### 2.1 append-only 的真实强度

上一版称「append-only 让预测不可篡改成为数据结构的自然属性」——这句话过强。纯文件加用户写权限，手工改一行或跑完再补预测都毫无阻力，工具无法阻止。

v1 不引入 hash chain（成本与收益不匹配），改为一条低成本的时序校验：

`run_result` 记录来源文件的 mtime；若该 mtime 早于对应 `prediction` 事件的 ts，事件中标记 `integrity: "result_predates_prediction"`，看板上显式标注。

这防不住有意伪造，但正好覆盖唯一会真正毁掉工具价值的行为——先看结果再写预测。

## 3. 数据模型

### 3.1 事件

`runs.jsonl` 每行一个事件：

```jsonc
{
  "v": 1,
  "ts": "2026-08-23T14:02:11+08:00",
  "type": "prediction",
  "batch": "b3",
  "run": "lr=1e-4,model=large",
  "payload": { }
}
```

`v` 是 schema 版本号，从第一行数据开始就带上，避免将来演进时无法区分格式。

事件类型：

| type | 说明 |
|---|---|
| `batch_opened` | 开启批次，内联假设全文、变量维度定义与指标规格 |
| `prediction` | 对某个 run 的预测。同一 run 只接受一次 |
| `prediction_revised` | 修订预测，保留原值引用，看板标记「已修订」 |
| `run_result` | 单次实测结果（一个 seed 一条），含来源溯源信息 |
| `reflection` | 复盘。作用域为单个 run 或整个 batch |
| `belief_added` | 新增一条信念 |
| `belief_weakened` / `belief_reinforced` / `belief_refuted` | 信念状态变更，引用信念 ID |
| `note` | 自由笔记 |

### 3.2 假设与信念的不可变引用

- `batch_opened` **内联假设全文快照**，不引用外部文件路径。批次的假设是当时那一刻的陈述，事后必须能原样还原。
- 信念使用**不可变短 ID**（如 `bel-7a3c`，内容 hash 前 4 位），不使用序号。上一版用 `#3` 这类序号引用手写 markdown，插入或删除一条就会让历史上所有引用的语义静默漂移——这是会污染全部历史数据的缺陷。
- `beliefs.md` 由 `belief_*` 事件派生渲染，展示时用人类可读的编号，但编号只是渲染层的产物，事件里存的始终是 ID。

### 3.3 Run 的标识

Run 由**变量组合**定义，不用自增 ID。实际主键是 `(batch, run)`——同一变量组合可以在不同批次中重复出现，两者是不同的 run。

开批次时声明变量维度，例如 `lr: [1e-3, 1e-4] × model: [base, large]`，笛卡尔积生成 4 个 run。

**规范化规则**（必须严格实现，否则 `1e-4` 与 `0.0001` 会分裂成两个 run）：

1. 键按字典序排列。
2. 值：可解析为数值的一律 `format(float(v), ".12g")`；布尔值统一 `true` / `false`；其余按字符串处理并 strip。
3. `k=v` 以 `,` 连接；值中若含 `,` 或 `=`，做百分号转义。

**变量维度不可中途扩展。** 批次开启后维度即锁定；需要新增维度就开新批次，`batch_opened` 中可声明 `derived_from: "b3"` 保留谱系。允许中途加维度会让批次内已有的 run key 全部失效，是纯粹的复杂度来源。

### 3.4 重复实验：seed 是 run 内的样本维度

**seed 不进 run key。** 同一变量组合换 seed 跑多次，写入多条 `run_result`，每条带 `seed` 字段，同属一个 run。

```jsonc
// run_result payload
{
  "seed": 0,
  "metrics": { "top1_acc": 0.831 },
  "source": { "path": "logs/large_1e-4/s0/results.json", "kind": "structured", "mtime": "..." }
}
```

这样设计的理由：

- 预测的对象是**该配置的期望表现**，不是某一次的抽签结果。把 seed 塞进笛卡尔积会让预测表膨胀 3–5 倍，而其中每一行的预测内容完全相同——纯摩擦，零信息。
- 多个 seed 的结果天然给出了该指标的**噪声水平**，这是下面阈值判定的基础。没有它，SURPRISE 判定就是在判定噪声。

判定时用各 seed 的均值与预测比对；样本标准差 `sd` 由系统自动计算并缓存为该指标的噪声估计。

### 3.5 指标规格

指标的比较方式必须逐个声明，在 `batch_opened` 中给出：

```jsonc
"metric_specs": {
  "top1_acc":   { "direction": "higher_better", "compare": "absolute", "tolerance": 0.005 },
  "train_loss": { "direction": "lower_better",  "compare": "relative", "tolerance": 0.10 }
}
```

上一版对所有指标统一使用 10% 相对偏差，在科研语境下不成立：`top1_acc` 从 0.80 到 0.84 只有 5% 相对偏差却可能是重大提升；`train_loss` 从 0.31 到 0.34 是 10% 却可能无所谓。绝对/相对、指标方向、容差三者必须 per-metric。

`ari plan` 为常见指标名（`*_acc`、`*_loss`、`ppl`、`f1`、`auc` 等）预填合理默认值，用户可改。

### 3.6 预测

```jsonc
{
  "metrics": { "top1_acc": [0.80, 0.84], "train_loss": 0.31 },
  "confidence": "medium",
  "rationale": "large 模型容量翻倍，但数据量没变，预期收益被过拟合抵消一部分",
  "expected_ranking": ["model=large", "model=base"]
}
```

- `metrics` 同时支持点估计与区间。区间通常更诚实，也让差异判定更有意义。
- `rationale` 是整个设计中最关键的字段。缺了它，事后只知道「猜错了」，无法定位**错的是哪个假设**，自学习无从谈起。因此它是必填项。
- `expected_ranking` 可选，作用域是 batch 而非 run。它必须声明**基于哪个指标**排序，否则多指标时无法判定：

```jsonc
"expected_ranking": { "metric": "top1_acc", "order": ["model=large", "model=base"] }
```

### 3.7 修订策略

绝对禁止修改会迫使用户绕过工具（例如发现预测时单位写错）。因此：

允许修订，但写入新的 `prediction_revised` 事件，保留原值，看板上永久标记「已修订」并可展开查看原始预测。

这是诚实与可用之间的平衡点。硬性禁止在实践中会失效。

### 3.8 判定：两个正交的轴

上一版把 `CLOSED` 与 `CONFIRMED` / `SURPRISE` 混在同一个状态集合里，且 `PENDING` 同时承担「尚无结果」与「抽取存疑」两种语义。本版拆成两个正交的轴。

**轴一：verdict（判定结果）**

| verdict | 判定 |
|---|---|
| `NO_RESULT` | 尚无任何实测结果 |
| `UNVERIFIED` | 有结果但来源存疑，待人工确认 |
| `CONFIRMED` | 落在预测区间内，或偏差在判定阈值内 |
| `SURPRISE` | 超出判定阈值，**无论方向** |
| `NOISY` | seed 间标准差已超过判定分辨率，本次判定无效 |

**轴二：closure（是否已复盘）** —— `OPEN` / `CLOSED`，由 `reflection` 事件驱动。

单指标判定阈值。先定义**判定分辨率** `resolution`：预测为区间时是区间宽度 `b - a`，预测为点估计时是容差 `tol`（`compare` 为 absolute 时即 `spec.tolerance`，为 relative 时是 `spec.tolerance * |p|`）。

```
1. 噪声守门（sd 已知时）：2 * sd > resolution  → NOISY，判定终止
2. 否则：
   区间 [a, b]：mean ∈ [a, b]      → CONFIRMED，否则 SURPRISE
   点估计 p：  |mean - p| ≤ tol   → CONFIRMED，否则 SURPRISE
```

噪声守门必须在判定之前，且守门通过后阈值就是 `tol` 本身——因为守门已经保证了 `2 * sd ≤ tol`，再取 `max(tol, 2*sd)` 是恒等操作。

`NOISY` 的含义是：这个实验设计分辨不出你要问的差异。此时看板不报 CONFIRMED/SURPRISE，而是提示「需要更多 seed，或该指标的差异小于噪声」。这比给出一个假的 CONFIRMED 有价值得多。

**run 级 verdict 的优先级**（取最坏）：`SURPRISE` > `NOISY` > `UNVERIFIED` > `NO_RESULT` > `CONFIRMED`。即只有全部指标都 CONFIRMED 时 run 才是 CONFIRMED。

**run 级聚合**：取最坏——任一指标 `SURPRISE` 则 run 为 `SURPRISE`；`review` 时必须点名是哪个指标错了，而不是笼统地说这个 run 不符预期。

### 3.9 batch 级判定

很多假设本来就是批次级的（「大模型会比小模型好」），且相对排序通常比绝对值更容易预测准、也更有信息量。因此 `expected_ranking` 需要独立的判定路径：

- 按 `expected_ranking.metric` 的实测均值排序，用该指标 spec 的 `direction` 决定谁算「更好」。
- 遍历 `order` 中所有有序对 `(a, b)`（a 应优于 b）：若实测中 a 未优于 b，即为一次翻转。
- 该对的差值落在噪声内（`|mean_a - mean_b| ≤ 2 * max(sd_a, sd_b)`，并列视为落在噪声内）→ 记为 noisy 翻转；否则记为 real 翻转。
- 存在 real 翻转 → `SURPRISE`，并指出具体哪几对翻了；否则存在 noisy 翻转 → `NOISY`；全部命中 → `CONFIRMED`。

batch 级 verdict 与 run 级 verdict 相互独立，看板分开展示。全部 run 都 CONFIRMED 但排序翻了，是一个非常有价值的信号，不能被 run 级的全绿淹没。

**批次信息量提示**：如果一个批次全部为 CONFIRMED 且排序也命中，`ari board` 主动提示「本批次未产生新信息，变量取值范围可能过于保守」。这条直接对应「最怕没有起伏的实验」这一原则。

### 3.10 闭环规则

- **每个 `SURPRISE` run 必须单独写 `reflection`**，未复盘的持续钉在看板顶部。
- **`CONFIRMED` run 允许由一条 batch 级 `reflection` 统一收口**，不要求逐个写。上一版要求所有 run 都写反思才算 CLOSED，但同一份文档又说全 CONFIRMED 的批次没产生新信息——让人给 8 个全中的 run 逐个写反思是纯摩擦。
- **batch 可关闭的条件**：所有 run 都已有可判定结果（不存在 `NO_RESULT` / `UNVERIFIED` / `NOISY`）+ 所有 SURPRISE 已复盘 + 存在一条 batch 级 reflection。旧规则只检查 SURPRISE，会让完全没结果的批次也被标为已收口，v0.2 已修正。

这是对抗「自动抽取导致跳过思考」的具体机制——自动化降低了记录成本，但不能降低思考成本。

## 4. CLI 兼容入口（v0.1）

```
ari init <project>       建立目录骨架
ari plan                 开批次：写假设、声明变量维度与指标规格，填预测表并锁定
ari result <path|-->     录入实测：解析 results.json / metrics.csv，或交互式手填
ari review [run]         逐个处理 SURPRISE，追问原因，写入 reflection
ari board                渲染看板（含 beliefs.md 重新生成）
```

推迟到 v1.1 的命令：`ingest`（LLM 日志抽取）、`export --xlsx`、`ask`。

### 4.1 `ari plan` 的历史交互形态

**批量编辑，不做逐项问答。** `ari plan` 生成一份预填好全部变量组合、带注释的 YAML 草稿，用 `$EDITOR` 打开，用户一次填完，保存退出后校验并写入事件流锁定。

```yaml
# 批次 b3 —— 保存退出即锁定，之后只能通过 prediction_revised 修订
hypothesis: |
  <在这里写这一轮要验证什么>

runs:
  - run: lr=0.0001,model=base
    top1_acc:   # 点估计或区间，如 0.80 或 [0.80, 0.84]
    train_loss:
    confidence: # low / medium / high
    rationale:  # 必填：你为什么这么预期
  - run: lr=0.0001,model=large
    ...

expected_ranking:  # 可选，按你预期的从好到差排列
```

选批量编辑而非 TUI 逐项问答的理由：填第 3 行预测时人会回头参考前两行，这个横向比较既降低摩擦，也实实在在提高预测质量——逐项问答恰好把这个能力关掉了。

预测填写摩擦是本项目的头号风险。v0.2 将这套“两段式思考”迁移到同一 GUI 页面，通过动态表格保留横向比较能力，不再要求用户编辑 YAML。

### 4.2 AI 的那份预测：不给数值

Agent 会同时生成自己的一份判断，但**在用户填写完成之前不显示**。先看到 AI 的预测会产生锚定效应，用户自己的预测随之失去独立性，而独立性正是这个机制价值的来源。

但 AI 侧的输出限定为三项，**不包含具体数值点估计**：

1. 预期的相对排序；
2. 定性方向（哪个变量的影响更大、朝哪个方向）；
3. 用户可能没考虑到的混淆因素。

理由：通用模型对「你的私有数据集上 large 比 base 高几个点」没有任何有效先验，给出的数字看似精确实则编造。第一次出现明显离谱的数值就会把信任耗光，而这个功能的全部价值都建立在信任上。相对排序与混淆因素提示则是模型真正有优势的地方。

填写完成后并排展示双方判断。分歧本身是有信息量的信号——它提示了领域直觉与通用模型认知的差异所在。

## 5. 结果录入（v1）

v1 只做确定性解析，不调用 LLM：

1. **结构化文件** —— `results.json` / `metrics.csv` 存在时直接解析。
2. **交互式手填** —— `ari result --` 打开与 plan 同构的 YAML 草稿，填实测值。

### 5.1 run 对齐

在 `ari plan` 阶段就声明日志路径模板，例如：

```yaml
result_path: "logs/{model}_{lr}/s{seed}/results.json"
```

由模板反解得到 `(run, seed)`，确定性对齐，无歧义。上一版设想的「依据训练脚本命令行参数自动对齐」依赖日志里打印了完整命令行，很多脚本不打；模板方式把这件事前置成一次性声明，稳得多。

模板匹配不上的文件不静默跳过，明确列出并要求处理。

### 5.2 确认与溯源

- 解析结果不直接落盘。先展示「抽到了这些，对吗？」等待确认。错误的指标进表比缺失指标更有害。
- 每条 `run_result` 记录来源：文件路径 + 定位信息（JSON path / CSV 行号）+ 解析方式 + 文件 mtime（用于 2.1 的时序校验）。
- 指标名在结果文件中不存在时，明确报告缺失，不静默填空。

### 5.3 v1.1 的日志抽取层

留作后续，设计方向已明确，此处仅记录以免丢失：

- **模板层** —— 某个日志格式被成功抽取并经用户确认后，将模式固化到 `extractors/`，同一格式后续不再调用模型。
- **LLM 兜底** —— 传入日志尾部与候选行，返回结构化 JSON，**且每个指标必须附带原文行号**。
- **用预测表约束抽取范围** —— 预测表已声明本批次关心哪些指标，以指标名 grep 出候选行配合日志尾部 N KB，即可覆盖绝大多数情况，无需将完整日志送入模型，也顺带解决大日志的上下文问题。
- **交叉校验** —— 结构化文件与日志文本都能取到同一指标时比对，不一致则报告并要求人工裁决。

## 6. 技术栈与模型配置

**Python ≥ 3.11**（`tomllib` 内置），`uv` 管理依赖。依赖控制在少数几个：CLI 框架、`rich`（终端看板）、`PyYAML`。事件读写手写，不引入 ORM。v0.2 的本地 GUI 使用标准库 HTTP 服务与随包静态资源，不要求联网下载前端依赖。

选 Python 的理由：科研生态原生，日志/CSV/Excel 处理现成，与目标用户（也包括自己）的环境一致。

```toml
[providers.openai]
base_url = "https://api.openai.com/v1"
api_key_env = "OPENAI_API_KEY"

[providers.anthropic]
base_url = "https://api.anthropic.com"
api_key_env = "ANTHROPIC_API_KEY"

[roles]
reason = "anthropic:<strong-model>"   # 复盘追问与 plan 阶段的定性判断
extract = "openai:<fast-model>"       # v1.1 日志抽取用，v1 不启用
```

- **按角色配置模型**，而非全局单一模型。抽取与推理的成本/能力需求差异很大。
- 密钥通过环境变量或系统 keychain 提供，不写入 `config.toml`——该文件要进 git。
- 适配器只需两个：OpenAI 兼容协议（覆盖绝大多数第三方平台）与 Anthropic。

## 7. 复盘与自学习

`ari review` 对每个 SURPRISE run：

1. 并排展示预测、实际（含各 seed 与标准差）、**具体是哪个指标偏了多少**，以及当初写下的 `rationale`。
2. Agent 追问——追问必须有针对性：检索本项目历史上相似的 SURPRISE 与 reflection，提出具体假设，例如「上次调低 lr 你也预期会涨、结果没涨，是否同一原因？」
3. 写入 `reflection`：`{ 原因假设, 涉及的信念 ID 及其变更, 下一步动作 }`

### 7.1 信念账本

信念以 `belief_added` 事件加入，以不可变 ID 被 reflection 引用（见 3.2），`beliefs.md` 是其渲染视图。

reflection 可标记「推翻了 `bel-7a3c`」或「强化了 `bel-91e0`」。这份账本是自学习的具体载体，同时也是将来撰写论文 discussion 部分的原材料。

## 8. 错误处理

| 情况 | 处理 |
|---|---|
| `runs.jsonl` 存在损坏行 | 逐行独立解析，跳过坏行并报告位置，不因一行损坏而使整个项目不可用 |
| 未知的事件 `type` 或更高的 `v` | 保留原行不丢弃，跳过并提示升级，不重写文件 |
| 解析结果不确定 | 标记 `UNVERIFIED` 交由人工，不猜测 |
| LLM 不可用 | 所有非 LLM 功能（plan、result、board）必须能离线工作；`review` 降级为无追问的纯手写模式 |
| 指标名在结果文件中不存在 | 明确报告缺失，不静默填空 |
| 结果文件 mtime 早于 prediction | 记录 `integrity` 标记并在看板标注，不阻断写入 |

## 9. 测试策略

- **规范化与判定：纯函数，严格断言。** run key 规范化（`1e-4` / `0.0001` / `1E-4` 必须同 key）、单指标判定、run 级聚合、`NOISY` 触发、排序逆序对——这几块是整个系统的地基，覆盖率要求最高。
- **状态机**：给定事件序列 → 期望的 (verdict, closure)。含损坏行、乱序 ts、重复 prediction 等异常序列。
- **解析层**：收集真实 `results.json` / `metrics.csv` 样本作为 fixture，严格断言数值与路径模板反解结果。
- **LLM 相关**：录制真实响应作为 fixture 回放，CI 不打真实 API。断言「输出结构合法 + 引用的行号在文件中真实存在」，不断言具体数值。
- **端到端**：完整跑通 `plan → result → review → board`，校验产物文件。

## 11. 已识别的主要风险

1. **预测的填写摩擦。** 头号风险，也是 v1 范围被压到最小闭环的直接原因。批量填写整张预测表信息量更大，但前期投入也更高；若摩擦过大，用户会退化为跑完再补预测——那将使整个机制失效。4.1 的批量编辑设计是当前答案，需要在自用中验证。
2. **自动抽取削弱反思。** 本设计最大的内在张力：自动化降低记录成本的同时，也降低了「停下来思考」的触发频率。缓解手段是闭环规则（SURPRISE 未复盘即钉在看板顶部）与确认环节。v1 不做自动抽取，正好为这个张力争取到观察窗口。
3. **噪声基线需要多 seed，而多 seed 需要算力。** 3.4 的设计假设用户愿意为同一配置跑 3 次以上。若实际只跑单 seed，`sd` 无从估计，判定退回纯 tolerance 阈值，`NOISY` 保护失效。此时看板应明确提示「本批次判定未经噪声校准」，不假装结论可靠。
4. **日志格式的长尾（v1.1）。** 模板层能否有效收敛，取决于个人日志格式的稳定程度。若每个项目格式都不同，模板层收益有限，成本回落到 LLM 层。
