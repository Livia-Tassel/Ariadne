# Ariadne v0.4 设计：台账界面与闭环补全

上游：[v0.2 GUI](2026-08-25-gui-v0.2-design.md) · [v0.3 桌面](2026-08-25-desktop-v0.3-design.md) · [领域规则](2026-08-23-experiment-loop-design.md)

## 1. 版本目标

v0.3 交付了可双击运行的桌面应用，但界面与功能都停在"能跑通"。v0.4 要解决两个具体问题：

**一、GUI 是 CLI 的严格子集，缺的恰好是让闭环显得聪明的那几块。** `advising.py`（锁定预测后给定性判断）、`probing.py`（复盘时的针对性追问）、`recall.py`（检索历史相似意外）在 `web.py` 与 `webui/app.js` 里零引用，只有 CLI 接了。按 `result_path` 模板自动发现结果文件同样只在 CLI。而 README 把桌面应用写成推荐入口——用户双击 `.app` 看到的是一个没有 AI、录结果只能手敲的版本。

**二、界面是通用 SaaS 仪表盘的默认形状。** 侧栏 + 卡片 + 五个统计瓦片 + 单一青绿主色 + Unicode 字符当图标。这套配方与"实验台账"这件事没有关系：它把所有内容压成同一视觉重量，把最有信息量的结果（意外）和最没有信息量的结果（计数）摆在同一层，并且用五个没有决策价值的数字占据首屏。

完成标准：打开应用的第一屏就告诉你现在该做什么；录一次结果不超过一次确认；锁定预测之后能看到 AI 的独立判断；界面看起来像一页实验记录，而不是一个后台管理系统。

## 2. 视觉方向：台账

选定方向是**台账**——纸与墨、细线代替卡片、唯一的饱和色留给"意外"。

### 2.1 原则

| 原则 | 具体做法 | 反面 |
|---|---|---|
| 内容有重量差 | 意外用印章红 + 左侧竖线；符合预期是纯墨色，不着色 | 现在每个判定都有自己的底色徽章，五种颜色平权 |
| 线，不是盒子 | 1px 细线分隔行；无卡片、无阴影、无圆角 | 现在一切都是 `--radius: 12px` + `--shadow` 的卡片 |
| 数据等宽，散文衬线 | 所有数字走 `tabular-nums` 等宽；假设、理由、复盘走衬线 | 现在正文与数字同一套无衬线，数字不对齐 |
| 密度是功能 | 行高紧凑，一屏能看完六个 run 的预测/实测/偏差 | 现在一个 run 要展开才能看到偏差 |
| 不用装饰图标 | 需要标记时用文字与线；不用 `◍ ◎ ▤ ✦ ✎ ⌁ ◷` | 现在导航与空状态全靠 Unicode 字符 |

### 2.2 令牌

```
纸    --paper #fdfcf8    墨   --ink  #191714
                          次墨 --ink2 #5f5850   三墨 --ink3 #98918a
线    --rule  #ddd7cc     重线 --rule-strong #191714
信号  --signal #ab2f22   （印章红，全站唯一饱和色）
散文  "Iowan Old Style", "Charter", Palatino, "Songti SC", "Source Han Serif SC", serif
数据  ui-monospace, "SF Mono", Menlo, monospace   —— 一律 font-variant-numeric: tabular-nums
```

深色模式保留同一结构：墨与纸互换，信号色提亮到 `#e0685a`，仍然只有一个饱和色。

### 2.3 判定的视觉编码

颜色不单独承载语义（可访问性）。每个判定同时有位置、字重与文字三重编码：

| 判定 | 编码 |
|---|---|
| 符合 | 纯次墨色文字「符合」，无底色，无竖线 |
| 意外 | 印章红文字「意外」+ 行左侧 2px 红竖线 + 偏差值加粗 |
| 噪声 | 次墨色文字「噪声」+ 偏差值改为虚线下划线，旁注 2σ 与分辨率 |
| 等待结果 | 三墨色文字「待录」，整行降到三墨色 |
| 待确认 / 完整性告警 | 印章红文字 + 整行红色细外框 + 一行原因 |

## 3. 信息架构

导航从五项收到四项：

```
今天    批次    账本    论文                              ⌘K
```

`想法` 与 `信念` 合并为「账本」的两节（在追 / 在册）。合并的理由不是省一个导航位：现在 `app.js` 里 `renderIdeas()` 与 `renderBeliefs()` 共用同一个 `.belief-grid`、同一套卡片结构、同一种"一行文本 + 一个 ID + 一个状态"的数据形状——它们本来就是同一种台账条目，只是处在管线的两端。

### 3.1 首屏「今天」

不放计数器，放一列排好序的待办。每行自己说清事由，不用点进去才知道发生了什么：

```
~/exp/lr-sweep · 6 批次 · 命中 23/31 · 待复盘 2
────────────────────────────────────────────────────────────
│ 待复盘   B03  large/strong   0.820 → 0.769   −0.051   写复盘 →
│ 待复盘   B03  base/strong    0.735 → 0.706   −0.029   写复盘 →
│ 预测缺席 B04  base/none      结果已在库，无法判定       锁预测 →
  新结果   B04  扫到 4 个结果文件                        核对 →
  等结果   B04  2 个 run 未跑完
  补 seed  B02  base/none      2σ=0.019 > 分辨率 0.005   补 seed →
  可收口   B01  结果齐、意外已复盘                        写结论 →
────────────────────────────────────────────────────────────
最近的落差   −0.051  −0.029  +0.011  −0.006  +0.002
```

排序即优先级，且顺序有依据：

1. **待复盘的意外** —— 信息量最大，且是唯一会随时间衰减的东西（隔一周你就想不起当时为什么那么预期）。带红竖线。
2. **预测缺席但结果已在库** —— 见 §4.2。这是本工具要防的那件事，必须排在前面且带红竖线。
3. **新扫到的结果文件** —— 一次确认就能入库，动作成本最低。
4. **等结果 / 补 seed / 可收口** —— 按批次归并，不逐 run 罗列。

"最近的落差"是校准记录的种子：一条窄带列出最近 N 次意外的偏差，让你看见自己是不是系统性高估。不单开一页。

空项目时首屏不是"记想法 → 立项 → 表单墙"三跳，而是直接就地一个能提交的最小批次表单（§5.1）。想法降级为可选来源，不再是入口。

## 4. 领域层：让不诚实的状态响起来

这一节是纯 Python 改动，不涉及界面，但它是其余一切的前提。

### 4.1 `result_path` 与 `expected_ranking` 不再写死

`web.py:113` 把 `result_path=None`、`expected_ranking=None` 硬编码进 `Design`。后果比"少个便利功能"严重得多：

`project._check_integrity()` 靠结果文件的 `mtime` 早于 `prediction` 事件时间戳来标记 `result_predates_prediction`——先看结果再补预测的嫌疑。而 `mtime` 只存在于文件自动发现路径的 `payload.source` 里。手工录入没有 `source`，所以**GUI 建的每一个批次都拿不到这个检查**。GUI 因此不只是功能少，是把工具的核心承诺关掉了。

`expected_ranking=None` 同理让 `_finalize_ranking()` 永不执行，`app.js` 的 `rankingNoteHtml()` 对 GUI 建的批次是死代码。

两者都改为 `create_batch` 的可选入参，并在批次页可后续补填（§4.3 的新事件）。

### 4.2 结果先到、预测缺席

`judge_run({}, ...)` 返回 `NO_RESULT`。这是纯内核的正确契约（没有预测就没有可判定的东西），但投影层不能就这么显示出去：一个已经有实测值的 run 显示成"等待结果"是错的，而 `closure_blockers()` 报"还有 run 尚无结果"是**事实相反**。

渐进锁定（§5.2）让这个状态从罕见变成常见，所以处理方式要明确：

**永不拒绝真实测量，但永久记录顺序。** 事件流是只追加的唯一真相，拒绝写入一次真实的实验结果比记录下它更糟。所以：

- `project._finalize()`：若 `run.samples` 非空而 `run.prediction is None` → `run.verdict = Verdict.UNVERIFIED`，并 `run.integrity.append("result_without_prediction")`。复用 UNVERIFIED 现有语义（"来源存疑待人工确认"——无法验证一个不存在的预测），不动 `Verdict` 枚举，因为它是测试覆盖最高的内核，`worst()` 的序关系不该为一个投影层问题让路。
- `project.project()`：记录 `run.first_result_ts`。当 `prediction` 事件到达一个已有结果的 run → `run.integrity.append("prediction_after_result")`。**这比 mtime 检查更强**，因为它不依赖文件时间戳，无法通过 `touch` 绕过。
- `closure_blockers()`：`UNVERIFIED` 的措辞按 integrity 内容分化，不再统一报"还有结果待确认"。

这两个 integrity 标记都是不可变的、随事件流永存的、界面上显著可见的。工具的立场是：不阻止你事后补预测，但那条记录会一直带着这个标记。

### 4.3 新事件类型

```
batch_meta_revised   payload: { result_path?, expected_ranking? }
```

注册进 `_KNOWN_TYPES`。事件模型对扩展本来就友好（未知类型只警告不重写文件），但仍要显式注册，否则老版本 `ari` 读新项目会刷警告。

### 4.4 从 `cli.py` 提取共享的 AI 调用

`advise()`（`cli.py:199`）与 `probe()`（`cli.py:472`）目前住在 CLI 模块里，`web.py` 无法复用。把它们下移到 `advising.py` / `probing.py`，签名保持 `(root, ...) -> dict`，异常仍统一为 `LLMUnavailable`。CLI 改为调用下移后的版本，行为不变，测试不变。

## 5. 交互：把最高频的两件事做顺

### 5.1 建批次变轻

现在建一个批次要填：研究方向 + 假设 + 变量维度（名 + 取值）+ 指标（名 + 优化方向 + 比较方式 + 容差）+ 逐格 N×M 个预测值 + 每行置信度 + 每行理由。一个 2×3 设计是 24 个输入框，全在跑任何实验之前。第一次用的人在这里就走了。

改为**渐进锁定**。约束不变：某个 run 的预测必须先于它的结果。但这个约束是逐 run 的，不需要一次锁完整批。

- `POST /api/batches` 的 `predictions` 变为可选。最小可提交批次 = 假设 + 一行维度语法 + 一个指标名。
- 维度用一行紧凑语法：`model=base,large; aug=none,light,strong`。解析失败时就地报错并保留原文，不清空。
- 指标只需名字，方向与容差由 `defaultMetric()` 现有的推断规则给出（`acc|f1|auc|bleu` → 越大越好/绝对 0.005，`loss|ppl` → 越小越好/相对 0.1），显示为可改的次要信息，不是必填项。
- 预测表移到批次页。每个未锁定的 run 是一行内联表单：预测值 / 置信度 / 理由 / `锁定`。锁一个 run 是一个动作。先跑两个 run 也完全合法。

新接口 `POST /api/predictions`：为一批 run 写 `prediction` 事件。重复锁定同一 run 必须返回明确错误（投影层现在只是往 `run.warnings` 里塞一句"重复的 prediction 已忽略"，界面看不见），并提示改用修订路径。

### 5.2 录结果的主路径是自动发现

结果形态已确认：每个 run 一个 JSON/YAML，路径可套模板。所以主路径不是手敲。

```
POST /api/results/discover   { batch }
  → ingest.discover(root, batch.result_path, runs)
  → ingest.parse_result_file(path, metric_names)
  → { found: [{run, seed, metrics, source:{path, mtime}}], unmatched: [...], errors: [...] }
```

只读，不写盘。界面渲染成台账式确认表——CLI 那句"抽到了这些，对吗？"搬进 GUI，逐行可勾选，一次提交走现有 `/api/results`。

**`/api/results` 必须开始接受并写入 `source`。** 现在 `add_results` 不传 `source`，所以即使有了 `result_path`，`_check_integrity()` 依然拿不到 `mtime`。这是 §4.1 那条链的最后一环。

手工录入保留为退路，但从"一次一个 run 一个 seed 展开-填-提交"改为**整批一张表**：所有 run × seed 一个网格，Tab 横向流转，支持粘贴。现在 6 run × 3 seed 要 18 轮展开-提交，改完是一张表一次提交。

### 5.3 AI 层的三个接入点

全部可选，全部经 `LLMUnavailable` 静默降级——不配 `config.toml`、不设 API key、断网，界面行为不变，只是少那一段。

| 时机 | 模块 | 界面位置 |
|---|---|---|
| 锁定预测**之后** | `advising` | 批次页出现"看 AI 的判断"；给期望排序、各变量影响方向、可能忽略的混淆因素。不给任何数值（schema 层面保证）。 |
| 复盘时 | `probing` + `recall.similar` | 复盘表单里以一行提示出现（"两组的数据增强配置一样吗？"），对应 CLI 把追问写进草稿注释的做法。不是聊天框。 |

**锚定效应是硬约束。** `advise` 的调用必须在 `prediction` 事件落盘之后发起，不是"先算好晚点显示"——那时候根本还没算。渐进锁定下这意味着：至少锁定一个 run 之后按钮才出现。

输出一律只以 `note` 事件存档（`payload.kind = "ai_advice"` / `"ai_probe"`），**绝不参与判定**。verdict 永远纯离线可复现。

传输用同步 POST + 转圈，不做任务队列。理由：`ThreadingHTTPServer` 每请求独立线程，一次 AI 动作是用户主动触发且一次一个，`LLMUnavailable` 的降级路径已经存在。加一个硬超时（45s），避免死掉的 endpoint 把线程挂住。降级不是错误：返回 `200` + `{ok: true, available: false, reason}`，界面显示一行安静的说明，而不是红色报错。

## 6. 前端结构

`webui/app.js` 现在 1821 行单文件，界面面积要翻倍。选原生 ES 模块，不引构建链——`<script type="module">` 同源满足现有 CSP 的 `script-src 'self'`，零工具链，DevTools 里直接断点，py2app 照旧拷目录。

```
webui/
  index.html
  app.js              入口：路由 + 启动
  lib/dom.js          $ / $$ / esc / html 模板
  lib/api.js          fetch 封装与错误收口
  lib/fmt.js          fmt / fmtPrediction / dateLabel / 判定文案
  views/today.js      首屏待办
  views/batches.js    批次列表
  views/batch.js      批次详情
  views/ledger.js     账本（想法 + 信念）
  views/paper.js      论文列表
  views/draft.js      草稿详情
  parts/predict.js    渐进锁定表单
  parts/results.js    自动发现确认 + 手工表格
  parts/review.js     复盘表单 + AI 追问
  parts/advice.js     AI 判断面板
  styles.css
```

`web.py` 的 `_STATIC` 从写死的字典改为目录遍历。**这是安全相关改动**，必须：解析为绝对路径后校验仍在 `webui/` 之内（挡路径穿越）、只服务 `.html/.css/.js/.svg` 白名单后缀、保持现有全部安全响应头不变。字典写法是构造上安全的，遍历写法必须显式把这个性质补回来。

顺带修一个静默失效：现有 CSP 是 `style-src 'self'` 且没有 `unsafe-inline`，`app.js` 里那些 `style="margin:0"` 内联样式其实全被浏览器拦掉了。台账系统不需要内联样式，重写后自然消失。

## 7. 测试

判定内核（`runkey` / `verdict` / `metrics`）是纯函数、覆盖率要求最高，这一版**不动它**。新增覆盖集中在投影层与接口层：

- `test_project.py`：结果无预测 → `UNVERIFIED` + `result_without_prediction`；预测晚于结果 → `prediction_after_result`；`closure_blockers()` 措辞按 integrity 分化；`batch_meta_revised` 的投影。
- `test_web.py`：`/api/predictions` 渐进锁定与重复锁定拒绝；`/api/results/discover` 的 found/unmatched/errors 三分；`result_path` 与 `expected_ranking` 建批次后可读回；`/api/results` 写入 `source` 并触发 integrity。
- `test_resources.py`（已存在，未提交）：静态目录遍历的后缀白名单与路径穿越拒绝。
- AI 接口：无 `config.toml` / 无 API key 时返回 `200` + `available: false`，且**不写入任何事件**；有响应时只写 `note`，且 verdict 不变。

## 8. 实现阶段

每个阶段结束时应用可运行、测试全绿。

| 阶段 | 内容 | 为什么在这个位置 |
|---|---|---|
| 1 | 领域层诚实性（§4.1–4.4） | 纯 Python + 纯测试，不碰界面。后面所有阶段都依赖这里定下的状态语义。 |
| 2 | 前端拆模块 + 台账设计系统 + 今天/账本 IA（§2、§3、§6） | 行为不变，只换骨架与皮。必须早做：否则阶段 3–5 的界面工作要在 1821 行旧文件上写一遍、再随重写扔一遍。 |
| 3 | 录结果主路径（§5.2） | 最高频动作，收益最直接。依赖阶段 1 的 `result_path` 与 `source`。 |

## 9. 不做什么

- **不动判定内核。** `verdict` / `metrics` / `runkey` 的行为在这一版完全不变，`Verdict` 枚举不加成员。
- **不引前端框架与构建链。** 见 §6。
- **不做多项目工作区、不做云同步、不做协作。** 单人本地工具，数据留在用户电脑上这条不改。
- **不让 AI 参与判定。** 不做"AI 帮你写复盘"、不做"AI 建议改容差"。AI 只在锁定后给独立判断、在复盘时提一个具体问题，输出只进 `note`。
- **不做任务队列。** AI 调用同步 + 硬超时，见 §5.3。
